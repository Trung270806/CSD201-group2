\begin{abstract}
This report presents empirical performance evaluation and architectural analysis for the \textit{Bank Transaction History System} (Group 07, CSD201 Project). The system models real-time banking operations under strict compliance rules: prohibiting direct record deletion or modification (preserving auditability via \texttt{REVERSAL} transactions) and enforcing strict overdraft prevention. We experimentally investigate three core Research Questions (RQ1, RQ2, RQ3) comparing four custom-implemented data structures---Doubly Linked List, Binary Search Tree (BST), Hash Table, and Sorted Linked List---on a scale of 100,000 transaction records across 1,000 randomized queries. Experimental results demonstrate that BST pruning provides superior performance for range queries ($2.84\times$ faster than Doubly Linked List), binary search on linked lists fails to achieve logarithmic efficiency due to pointer traversal overhead and $O(N^2)$ insertion costs, and multi-criteria filtering easily satisfies the 200\,ms response time SLA threshold (achieving $< 0.20$\,ms per query).
\end{abstract}

\section{Introduction}
Modern core banking systems handle millions of daily transactions, demanding both strict auditing integrity and sub-millisecond query performance. In accordance with banking regulations, historical ledgers must be immutable: transaction deletion or modification is strictly prohibited, requiring corrective actions to be recorded as distinct \texttt{REVERSAL} transactions. Furthermore, account balances must strictly prevent unauthorized overdrafts during withdrawal operations.

As transaction volume scales to 100,000 records and beyond, linear storage mechanisms become performance bottlenecks. This experimental study addresses three key Research Questions (RQs) to guide data structure selection for real-time transaction management:

\begin{enumerate}
    \item \textbf{Research Question 1 (RQ1):} Does a Doubly Linked List, Binary Search Tree (BST), or Hash Table yield the fastest execution time when querying transaction history by timestamp range over 100,000 records --- measured across 1,000 randomized range queries?
    \item \textbf{Research Question 2 (RQ2):} Is Binary Search superior to Linear Search when searching for transactions by ID on a Sorted Linked List, and does the high cost of maintaining sorted order upon new insertion negate any potential search advantage?
    \item \textbf{Research Question 3 (RQ3):} Which data structure most efficiently supports multi-criteria filtering (date range + transaction type + amount range) simultaneously while maintaining a strict response time SLA under 200\,ms on a 100,000-record dataset?
\end{enumerate}

To ensure stability and eliminate random execution noise, all experiments are conducted with a fixed random seed and pre-warmed JVM execution cycles.

\section{RQ1: Timestamp Range Query Performance}

\subsection{Experimental Design and Methodology}
Range queries select all transactions occurring within a specified time window $[t_{\text{start}}, t_{\text{end}}]$. We measure the total execution time for 1,000 range queries on a dataset of 100,000 transactions across three data structures:
\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Custom Doubly Linked List:} Traverses all $N=100,000$ nodes sequentially from head to tail ($O(N)$ lookup).
    \item \textbf{Custom Hash Table:} Performs a linear scan over internal bucket arrays to evaluate timestamp constraints for all entries ($O(N)$ scan).
    \item \textbf{Custom Binary Search Tree (BST):} Nodes are ordered by timestamp string. Range retrieval uses subtree pruning ($O(\log N + k)$), skipping branches whose subtrees fall entirely outside $[t_{\text{start}}, t_{\text{end}}]$.
\end{itemize}

\subsection{Results --- Range Query Performance}

\begin{table}[htbp]
\centering
\small
\begin{tabular}{lrrr}
\toprule
\textbf{Data Structure} & \textbf{Total Time (ns)} & \textbf{Avg Time / Query ($\mu$s)} & \textbf{Speedup vs. DLL} \\
\midrule
Custom Doubly Linked List & 292,636,100 & 292.64 $\mu$s & $1.00\times$ (Baseline) \\
Custom Hash Table & 212,109,500 & 212.11 $\mu$s & $1.38\times$ faster \\
Custom Binary Search Tree (BST) & 103,071,100 & 103.07 $\mu$s & \textbf{2.84$\times$ faster} \\
\bottomrule
\end{tabular}
\caption{RQ1 Empirical Benchmark Results (100,000 records, 1,000 range queries).}
\label{tab:rq1}
\end{table}

\subsection{Analysis}
As demonstrated in Table~\ref{tab:rq1}, the Custom BST achieves the fastest execution time, completing 1,000 range queries in 103.07\,ms (103.07\,$\mu$s per query). This represents a \textbf{2.84$\times$ speedup} over the Doubly Linked List and a \textbf{2.06$\times$ speedup} over the Hash Table.

The mathematical basis for this performance gap lies in the algorithmic structural properties:
\begin{enumerate}[leftmargin=1.5em]
    \item \textbf{Hash Table Limitations:} Although a Hash Table provides $O(1)$ expected time for point lookups by transaction ID, hash functions destroy temporal ordering. Consequently, answering range queries requires iterating through all $N$ elements across all hash buckets ($O(N)$ complexity).
    \item \textbf{BST Pruning Advantage:} Because the BST maintains key order based on transaction timestamps, range traversal prunes subtrees where node values are strictly less than $t_{\text{start}}$ (ignoring left subtrees) or strictly greater than $t_{\text{end}}$ (ignoring right subtrees). This restricts traversal to relevant nodes ($O(\log N + k)$), dramatically reducing CPU comparison cycles.
\end{enumerate}

\subsection{Conclusion for RQ1}
For time-range transaction history queries over 100,000 records, the \textbf{Binary Search Tree (BST)} is the optimal data structure, outperforming both Hash Tables and Doubly Linked Lists due to subtree range pruning.

\section{RQ2: Binary Search vs. Linear Search on Sorted Linked List}

\subsection{Experimental Design and Hypotheses}
RQ2 examines whether maintaining a sorted linked list enables efficient binary search by transaction ID. We test two specific hypotheses:
\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Search Efficiency Hypothesis:} Does Binary Search achieve superior lookup times compared to Linear Search on a sequential linked list?
    \item \textbf{Insertion Cost Hypothesis:} Does the cumulative $O(N^2)$ cost of sorted insertion negate any search performance advantage?
\end{itemize}

To measure insertion overhead accurately without CPU freeze, sorted insertion performance is evaluated on $N=5,000$ records, followed by 1,000 transaction ID lookup queries.

\subsection{Results --- Sorted Linked List Performance}

\begin{table}[htbp]
\centering

\toprule
\textbf{Operation / Search Method} & \textbf{Total Execution Time (ns)} & \textbf{Avg Time per Op ($\mu$s)} \\
\midrule
Sorted Insertion Cost ($O(N^2)$ total) & 91,120,700 ns & 18.22 $\mu$s / insert \\
Linear Search by Transaction ID & 25,240,900 ns & 25.24 $\mu$s / lookup \\
Binary Search on Linked List & 15,279,000 ns & 15.28 $\mu$s / lookup \\
\bottomrule
\end{tabular}
\caption{RQ2 Benchmark Results on Sorted Linked List ($N=5,000$, 1,000 queries).}
\label{tab:rq2}
\end{table}

\subsection{Analysis}
While Binary Search appears marginally faster than Linear Search per lookup (15.28\,$\mu$s vs 25.24\,$\mu$s), the theoretical $O(\log N)$ divide-and-conquer advantage is fundamentally undermined by the linked list structure:
\begin{enumerate}[leftmargin=1.5em]
    \item \textbf{Pointer Traversal Overhead:} Unlike contiguous arrays offering $O(1)$ random indexing, locating the midpoint node in a linked list requires traversing $N/2$ pointers ($O(N)$ node hops). As a result, Binary Search on a linked list incurs $O(N)$ overall time complexity per search.
    \item \textbf{Dominant Insertion Overhead:} Maintaining sorted order during record ingestion requires comparing new transactions against existing nodes, resulting in $O(N^2)$ cumulative insertion time (91.12\,ms for 5,000 records). In dynamic banking environments with frequent real-time transactions, this massive insertion penalty completely negates the minor lookup difference.
\end{enumerate}

\subsection{Conclusion for RQ2}
Binary Search on a Sorted Linked List is \textbf{inefficient and impractical}. Pointer traversal prevents true $O(\log N)$ lookup scaling, and the severe $O(N^2)$ insertion overhead destroys operational feasibility. For ID lookups, a chained Hash Table ($O(1)$ expected lookup and $O(1)$ insertion) should be used instead.

\section{RQ3: Multi-Criteria Filtering and SLA Compliance}

\subsection{Experimental Design and Hypotheses}
Core banking dashboards require multi-criteria filtering where queries specify three criteria simultaneously:
\begin{enumerate}
    \item Date interval $[t_{\text{start}}, t_{\text{end}}]$
    \item Transaction Type (\texttt{DEPOSIT} or \texttt{WITHDRAWAL})
    \item Amount range $[amount_{\text{min}}, amount_{\text{max}}]$
\end{enumerate}
We evaluate whether candidate data structures can process multi-criteria queries across 100,000 records while maintaining a strict Service Level Agreement (SLA) threshold of \textbf{$< 200$\,ms per query}.

\subsection{Analysis}
All three data structures comfortably pass the 200\,ms SLA requirement by a substantial margin:
\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Custom BST Performance:} Achieves the fastest filtering time at \textbf{0.123\,ms per query} (123.14\,ms total for 1,000 queries). The BST leverages temporal pruning to first isolate a small candidate subset of matching dates, then evaluates Type and Amount bounds only on that filtered subset.
    \item \textbf{Doubly Linked List \& Hash Table:} Achieve 0.173\,ms and 0.202\,ms per query respectively. Even under full linear scans over 100,000 records, modern in-memory RAM execution speeds keep latency well below 1\,ms.
    \item \textbf{SLA Margin:} The worst average query latency (0.202\,ms) is nearly \textbf{1,000$\times$ faster} than the 200\,ms threshold, confirming robust system performance under heavy query workloads.
\end{itemize}

\subsection{Conclusion for RQ3}
The \textbf{Custom BST} is the most effective data structure for multi-criteria transaction filtering. All evaluated structures strictly comply with the 200\,ms SLA requirement for 100,000 records.

\section{Overall Conclusions}
\begin{enumerate}
    \item \textbf{Range Queries (RQ1):} The \textbf{Binary Search Tree (BST)} is the optimal structure for timestamp range searches ($2.84\times$ faster than Doubly Linked List), as key ordering enables efficient subtree pruning.
    \item \textbf{Sorted Linked List Lookups (RQ2):} Binary search on linked lists fails to achieve logarithmic performance due to sequential pointer traversals. The $O(N^2)$ insertion cost further renders sorted linked lists impractical for real-time transaction ingestion.
    \item \textbf{Multi-Criteria Filtering \& SLA (RQ3):} Combining BST date pruning with secondary criteria filtering yields the lowest latency (0.123\,ms per query). All structures successfully satisfy the 200\,ms SLA response threshold on 100,000 transaction records.
\end{enumerate}
