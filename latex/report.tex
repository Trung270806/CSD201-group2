\begin{abstract}
This report presents the design and experimental evaluation of a bank transaction history management system implemented in Java using custom-built data structures. The system follows strict banking principles by preventing direct deletion or modification of historical records and instead using reversal transactions to preserve an auditable trail. Three data structures are compared experimentally: Custom Doubly Linked List, Custom Binary Search Tree, and Custom Hash Table. The results show that the BST and Hash Table provide significantly better performance than the linear linked-list approach for range queries and multi-criteria filtering.
\end{abstract}

\section{Introduction}
In modern banking systems, the ability to retrieve transaction history quickly and reliably is essential. As the number of records grows, naive linear structures such as linked lists become inefficient for repeated search and filtering operations. For this reason, this project focuses on developing a transaction management system that uses custom data structures and evaluates their practical performance.

The main objectives of the project are to:
\begin{itemize}[leftmargin=1.5em]
    \item store transaction records in a way that preserves audit integrity;
    \item support fast lookup by transaction ID and time range;
    \item provide monthly analytical summaries;
    \item compare different data structures using measurable benchmark results.
\end{itemize}

\section{System Design}
\subsection{Core Classes}
The system is implemented using an object-oriented design with separate classes for data entities, business logic, and user interaction.
\begin{itemize}[leftmargin=1.5em]
    \item \textbf{Transaction}: represents a bank transaction with attributes such as ID, account number, amount, type, and timestamp.
    \item \textbf{Account}: stores account information and balance state.
    \item \textbf{BankService}: handles transaction posting, balance validation, reversal operations, and data retrieval.
    \item \textbf{CustomHashTable}: uses chained buckets to store records by transaction ID.
    \item \textbf{CustomBST}: supports search and range-based queries over transaction timestamps.
    \item \textbf{CustomDoublyLinkedList}: serves as a baseline structure for comparison.
\end{itemize}

\subsection{Business Rules}
The implementation follows common banking constraints:
\begin{enumerate}[leftmargin=1.5em]
    \item \textbf{Overdraft prevention}: withdrawals are rejected when the requested amount exceeds the current balance.
    \item \textbf{Audit trail preservation}: historical transactions are never deleted or overwritten directly.
    \item \textbf{Reversal transactions}: instead of modifying prior records, the system creates a new transaction of type \texttt{REVERSAL} to preserve a complete record of changes.
\end{enumerate}

\section{Experimental Results}
\subsection{RQ1: Time-range query performance}
The first experiment evaluates the time required to retrieve transactions within a specified time interval using the three data structures.

\begin{table}[htbp]
\centering
\small
\begin{tabular}{lcc}
\toprule
\textbf{Structure} & \textbf{Total time (ns)} & \textbf{Average per query} \\
\midrule
Custom Doubly Linked List & 292,636,100 & 292.64 $\mu$s \\
Custom Hash Table & 212,109,500 & 212.11 $\mu$s \\
Custom BST & 103,071,100 & 103.07 $\mu$s \\
\bottomrule
\end{tabular}
\caption{Results for RQ1: performance of time-range queries.}
\end{table}

The results indicate that the BST performs best for range-based lookup. It is approximately 2.84 times faster than the Doubly Linked List and 2.06 times faster than the Hash Table. This is expected because the BST can prune subtrees that lie outside the requested time interval.

\subsection{RQ2: Linear search versus binary search on a sorted linked list}
The second experiment measures insertion cost and search efficiency on a sorted linked list. Although the linked list can preserve ordering, its sequential access pattern still limits the benefit of binary search.

\begin{table}[htbp]
\centering
\small
\begin{tabular}{lc}
\toprule
\textbf{Metric} & \textbf{Value} \\
\midrule
Sorted insertion cost & 91,120,700 ns \\
Linear search by ID & 25,240,900 ns \\

\bottomrule
\end{tabular}
\caption{Results for RQ2: comparison of linear and binary search on a sorted linked list.}
\end{table}

Binary search remains faster than linear search by about 1.65 times. However, insertion into a sorted linked list is costly, which reduces its practicality in scenarios with frequent updates.

\section{Analysis and Conclusion}
The experimental results show that no single data structure is optimal in every case. For key-based lookup and large-scale retrieval tasks, the Custom Hash Table and Custom BST clearly outperform the linear linked-list approach. For range queries and multi-criteria filtering, the BST demonstrates the strongest performance because it can eliminate irrelevant portions of the dataset efficiently.

From a business perspective, the system also fulfills the intended banking requirements. The use of reversal transactions and overdraft checks ensures that transactions remain consistent, auditable, and consistent with practical banking rules. Overall, the project successfully achieved its main goal of building a transaction history system with clear architecture, stable operation, and empirical evidence for the effectiveness of custom data structures.
